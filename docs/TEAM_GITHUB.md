# GitHub в совместном проекте

Кандидат для #156. В production эта часть пока не установлена. Она дополняет Files/Git и существующую подготовку commit/push/PR; ключи и GitHub-вход остаются на компьютере действующего пользователя.

## Как пользоваться

1. Открой совместный проект → **Моя рабочая папка** и подключи свою копию указанного репозитория. У каждого участника своя папка, Git и Current Chat.
2. Во вкладке **GitHub** нажми **Проверить мой доступ**. Появятся фактический GitHub-аккаунт и его права. Если аккаунт верный, отдельная кнопка позволяет показать эту связь участникам проекта.
3. Загрузи issues или pull requests, при необходимости введи поиск. Открытая карточка показывает автора, состояние, описание, назначенных участников, комментарии, а для PR — ветку, точный SHA, ревью и доступные проверки этого SHA. Данные запрашиваются по действию; вкладка не опрашивает GitHub постоянно.
4. **Связать с проектом** сохраняет просмотренную версию в общих материалах GitHub. Из сохранённой карточки **В мой план работы** создаёт назначенный тебе обычный общий Plan. Выполнение начинается только через его обычную подготовку и подтверждение для твоего Current Chat.
5. В сохранённом общем материале кнопка **В GitHub**, а в Bridge — **Связать с GitHub**, открывает подготовку issue или связывание существующего issue/PR. Текст сначала виден в черновике, его можно изменить. Личный источник, переписка и последующие сообщения автоматически не публикуются.

Новое issue, комментарий, закрытие/повторное открытие issue и запрос ревью имеют два шага: **Проверить перед отправкой**, затем **Подтвердить в GitHub**. Между ними видны точный текст, репозиторий, действующий аккаунт, выбранный получатель и версия PR. Подготовку можно отменить. Свёрнутый редактор и закрытие окна сохраняют черновик на этом устройстве в пространстве текущего пользователя.

## Участники и доступ

Участник CodexWeb и GitHub collaborator — разные сущности. Приглашение в приложение не выдаёт права на репозиторий и не входит за человека в GitHub.

Владелец проекта может отдельно пригласить участника в GitHub с чтением или записью либо отозвать доступ. Для этого на его компьютере GitHub должен подтвердить административные права на репозиторий. Сначала выбирается человек из участников проекта, затем проверяется его GitHub-аккаунт. Подтверждённый самим участником аккаунт подставляется в поле; владелец может явно исправить его перед просмотром действия.

Существующее приглашение или доступ показываются без повторного приглашения и без скрытого повышения прав. Для прежнего участника сохраняется возможность отдельного отзыва GitHub-доступа. Отзыв доступа к проекту или отключение пользователя в Hub сами по себе не выполняют GitHub-запросы. Запрос ревью PR доступен участнику с правом записи в проект и подходящими правами GitHub; он также выбирает человека явно.

## Подтверждения и восстановление

Hub сохраняет владельца операции, выбранную рабочую папку, эпоху доступа, ревизию участия, исходный запрос и неизменяемую квитанцию подготовки. Компьютер отдельно сохраняет привязку к физическому корню, origin, GitHub user ID, repository ID и точному запросу. Перед отправкой повторно проверяются текущие аккаунт, права и версия issue/PR. Смена пользователя, папки, репозитория, членства или SHA не переносит разрешение на новый контекст.

При потере ответа состояние может быть **Исход пока неизвестен**. **Проверить исход** читает квитанцию и проверяет постусловия, а не отправляет действие повторно. До выяснения результата новая операция этого пользователя в репозитории блокируется. Создание issue и комментария сверяется по точному тексту, автору и отдельному невидимому HTML-маркеру квитанции. Не найденный в ограниченном окне результат остаётся неизвестным — это не доказательство, что отправки не было.

Просмотренные версии GitHub неизменяемы. Обновление того же запроса в другом окне не заменяет уже выбранную карточку. Если общую связь успели обновить после её просмотра, создание Plan требует просмотра новой версии. Точный повтор уже выполненного запроса возвращает прежний Plan.

Отзыв доступа запрещает новую отправку и выдачу позднего ответа. Если GitHub уже выполнил действие, квитанция сохраняется у исходного автора. Повторное приглашение того же человека не оживляет старое разрешение на отправку. Все незавершённые и неизвестные операции входят в проверку обслуживания Hub; смена checkout/владельца не обрывает их путь проверки.

## Границы реализации

- Браузер передаёт типизированное действие в Hub. Нельзя выбрать произвольный endpoint, команду, GitHub hostname, машину другого пользователя или токен.
- Windows использует существующую отдельную фиксированную Scheduled Task в пользовательском сеансе. Новый probe входит в установочный пакет; нужны обновлённые `DeliveryWorker.cjs`, `githubWorkProbe.js` и `Install-Delivery.ps1`. Нет нового сетевого listener и копирования credentials.
- Поиск ограничен одним проверенным репозиторием. Списки и комментарии выдаются страницами по 20, не более 50 страниц. Описание ограничено 20 000 символами, отправляемый текст — 16 000. Сокращение показывается явно.
- Ревью/проверки PR ограничены 50 записями каждого вида. Недоступные сведения о проверках не превращаются в сообщение об успехе. GitHub Actions не запускаются и не являются условием работы приложения.
- Сверка потерянного issue/комментария или приглашения ограничена 500 записями. Если исход нельзя однозначно установить, сохраняется неизвестное состояние и требуется разбор, без обхода новым UUID.
- До 100 сохранённых наблюдений на пользователя/проект, 5 000 квитанций на проект и 10 000 на машине. Старые наблюдения очищаются; общие опубликованные карточки и квитанции операций сохраняются.
- Машина сериализует изменения одного репозитория. При аварии основного процесса блокировка освобождается после проверки завершившегося PID. Одновременное восстановление сериализовано отдельным коротким guard; авария внутри самого восстановления блокирует дальнейшее автоматическое освобождение и требует проверки оператором. Нельзя удалять guard или квитанции при живом helper.
- Merge, force push, релизы, автоматическое одобрение PR и зеркалирование всего чата не добавляются этим модулем. Существующий явный commit/push/создание PR остаётся отдельным процессом Delivery.

## Проверки и источник контракта

Проверки используют отдельные SQLite/локальные Git-копии, два пользователя и подставной machine-local `gh`. Реальные issues, комментарии, приглашения и рабочий desktop владельца в тестах не изменяются. Это проверяет обработку запросов, прав, версий и сбоев, но не заменяет приёмку настоящего аккаунта/компьютера друга.

Официальные контракты: [Issues](https://docs.github.com/en/rest/issues/issues), [комментарии](https://docs.github.com/en/rest/issues/comments), [collaborators](https://docs.github.com/en/rest/collaborators/collaborators), [приглашения](https://docs.github.com/en/rest/collaborators/invitations), [запросы ревью](https://docs.github.com/en/rest/pulls/review-requests). Worker закрепляет поддерживаемую [версию REST API](https://docs.github.com/en/rest/about-the-rest-api/api-versions) `2022-11-28` и использует существующий вход `gh` действующего пользователя.
