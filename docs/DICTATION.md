# Message dictation

The microphone beside Send toggles recording in Codex and GPT. The first tap records; the second stops, transcribes and submits the combined typed/dictated text and current attachments through the normal send/queue flow. Native ownership handoff and permission checks still apply. A separate Cancel discards recording. Recognition or submission failure preserves the draft; retrying an uncertain recognition acknowledgement reuses its receipt. Repeated taps must not duplicate a send.

The compact recording strip shows elapsed time and a scrolling waveform measured from microphone amplitude. The audio analyser never connects to speakers and is closed with capture. If metering is unavailable the strip stays quiet rather than simulating speech. Both focused message fields grow with their content up to twice their normal height, then scroll internally; shortening or leaving the field restores compact sizing.

Recognition uses the owner's existing consumer ChatGPT session in the private Linux browser. The bridge submits a multipart audio file to ChatGPT's native `/backend-api/transcribe` route, the same consumer route documented in the official Codex voice client source (`openai/codex`, `rust-v0.105.0`, `codex-rs/tui/src/voice.rs`). The native service selects the recognition model; we do not claim a particular current model version. No API billing key, alternate recognition provider, local Whisper or browser speech-recognition fallback is used.

The browser asks for microphone permission only on an explicit click. Recording is bounded to three minutes and 6 MiB. Safari-compatible MP4 is preferred; other browser-supported audio formats are accepted. Microphone tracks stop on the second tap, Cancel, navigation, page hiding or session termination. Changing the chat discards late microphone grants and recognition results. Backgrounding or reaching the recording limit can preserve recognized text as a draft but never sends it. This is message dictation, not a background recorder or live voice conversation.

Audio travels through the authenticated, CSRF-protected Hub to the existing private GPT connector. The original ChatGPT token remains inside its browser origin. The public client gets only availability, operation state and recognized text. Audio is not written to Hub files or conversation history. Receipts belong to the exact login session and audio hash, expire after 15 minutes, and are removed after successful insertion or cancellation. The client retains the recording in memory after a recoverable failure. Explicit Retry reuses the same receipt after a lost acknowledgement; a confirmed failed recognition can be processed again. Reloading loses an unfinished recording, while already inserted text follows the normal saved-draft behavior.

Native WAV and browser-recorded MP4/WebM synthetic Russian fixtures were successfully transcribed against the existing account without sending a chat message. Hub tests cover authentication, CSRF, size/type limits, exact retry, cancellation and provider failures. Chromium/WebKit UI checks use simulated microphone hardware and exercise both composers, draft edits, cancellation, delayed permission, lost acknowledgements and phone/tablet layouts in all four themes. Actual iPhone microphone/permission behavior remains the owner's physical-device usage check; Linux WebKit does not provide native MediaRecorder in this test image.
