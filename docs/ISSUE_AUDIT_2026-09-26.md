## Подтверждённые технические остатки

### 1. GPT: история стоит за отправкой — #220

В `apps/hub/src/gpt-native.ts` запросы попадают в одну очередь; `drain` выполняет `await entry.run()` последовательно. Приоритетные entries могут менять очередность, но не освобождают уже занятую очередь. В `ops/gpt-native/service.mjs` после отдельных исключений `status/readLive` стоит общий `if (this.busy) fail('BUSY')`. Обычный read разделяет эту блокировку с mutation. В `gpt.ts` также остаются более широкие `hasUnfinishedJobs()` guards; их назначение следует проверить по каждому operation, а не удалить механически.

Следствие по структуре кода: даже чтение другой беседы в том же личном runtime может ждать зависшую операцию. Ранее сделанные chat-scoped outbox guards и ограничение повторных dispatch checks нужны, но не разделяют очередь transport/service. Новый кэш тоже не решит недоступность незакэшированного чтения.

Этап: ограниченный независимый read lane, coalescing одинаковых reads, честное разделение read health и write readiness; serialize mutations, учитывать точный conversation/project и личный runtime. Сохранить общий upstream cooldown/rate limit, numeric account binding, права, receipts и запрет replay uncertain sends. Проверить, какие native reads действительно безопасно перекрывать; renderer-зависимые операции не объявлять read-only только по названию.

Минимальная проверка: удержанная dispatch confirmation в A; чтение A/B, catalog/models/Results отвечает в пределах бюджета; read failure не портит outbox; две новые беседы без native ID не объединяются; ручное recovery доступно; три неудачные проверки останавливают background recovery этого job без остановки остальных. Дальнейшие широкие locks Team GitHub/Issue Drawer — отдельные меньшие остатки, описанные в [аудите очередей](ASYNC_ISOLATION_AUDIT_2026-09-26.md).

### 2. Codex: disconnect уничтожает runtime — #229

`ops/windows/companion/CodexWebBridge.cs:91` задаёт Job Object flag `0x00002000` с комментарием о завершении дерева процессов при disconnect. Bridge владеет pumps к stdin/stdout дочернего App Server; cleanup в строке 118 вызывает `child.Kill()` и ждёт завершение. Это подтверждает проблему жизненного цикла, а не только неудобную блокировку обновления.

Нельзя исправить её удалением `Kill()` или idle guard: потерянные stdio, ответ на approval, отсутствующий event backlog и два одновременно подключённых writer остаются нерешёнными. Нужен постоянный владелец App Server на стороне Companion с точным runtime identity, writer lease/generation, ограниченным журналом событий/состояния и проверяемым reattach. Потерянные ответы восстанавливаются чтением состояния, не повторной отправкой prompt или terminal input.

Проверка на disposable runtime: Hub теряется во время turn, turn завершается без Hub, approval приходит в его отсутствие, reconnect нескольких проектов, устаревший writer, другой пользователь/checkout, неизвестная отправка. Обновление самого Companion остаётся отдельной idle-only операцией с backup и hashes; проверить именно установленный Scheduled Task/Companion через Hub → SSH. Не испытывать disconnect на работающих чатах владельца.

**#132 уже закрыта, но её текст acceptance обещает переживание перезапуска web/API, не только статической веб-части.** Текущая реализация разделения публикации UI и engine не доказывает это широкое обещание. Незавершённую runtime часть следует явно связать с #229; закрытый статус #132 не считать доказательством живучести engine restart.

### 3. Внутренний GitHub не охватывает обычный assistant Markdown — #181

`Chat.tsx` и `GptWorkspace.tsx` используют `useArtifactComponents`. В `ArtifactMarkdown.tsx:211–225` обычная внешняя ссылка превращается в `<a target="_blank">` / `window.open`, без GitHub object resolver. `HumanReferences.tsx:104` отдельно распознаёт только `/issues/N` и `/pull/N`; commit URLs не входят даже в этот маршрут.

Встроенный GitHub viewer уже существует, поэтому нужны общие parser/resolver и internal navigation для commit/Issue/PR из всех подходящих источников. Проверять numeric repository, пользовательский checkout и текущий доступ; не выводить capability из совпавшего номера Issue или имени repo. Внешний GitHub оставить вторичным действием. Связать это с #224 source breadcrumbs и #227/#228 едиными окнами.

1. Не восстанавливать Reports, Canvas, отдельную Preview кнопку и промежуточный action-only экран Results. Поздние решения владельца имеют приоритет над текстом старой issue.
2. Не выдавать Admin вместо согласованного GitHub Write и не считать Hub membership безусловным доступом к чужому GitHub/PC.
3. Не заставлять пользователя заново создавать общий синтетический проект, переонбордить исходного владельца или повторно подключать «первого второго участника». Базовая реальная работа подтверждена 22 сентября; сегодняшний offline — другой вопрос.
4. Не объявлять обязательным коммит CODEXWEB.md. Актуальный профиль опционален и личный; AGENTS.md сохраняется. Динамические capabilities не становятся правами через текст инструкции.
5. Не вводить обратно ограничения ручного редактора на время работы Codex. Parser budgets, передача файлов и manual write authorization — разные границы.
6. Не заменять исправление причины очередным баннером/Retry и не дожимать неопределённые отправки. История и другие чаты должны жить независимо, uncertain receipts сохраняются.
7. Не закрывать #10 по WebKit screenshots и не выдавать исходники/собранный временный probe за проверку реально установленного Windows helper.
